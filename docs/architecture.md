# CCS Hub — System Architecture

## Overview

CCS Hub is a full-stack monorepo for the College of Computer Studies (CCS) at Quezon City University (QCU). It provides a unified platform for students, faculty, and administrators to manage academic activities, events, consultations, grades, and organizations.

## Monorepo Structure

```
ccs-hub/
├── apps/
│   ├── api/        Node.js + Express + TypeScript REST API
│   ├── web/        React + Vite single-page application (admin/faculty portal)
│   └── mobile/     Expo React Native application (student-facing)
├── packages/
│   └── shared/     Shared TypeScript types and Zod validation schemas
├── docker/
│   └── postgres/   PostgreSQL initialization SQL
└── docs/           Architecture and ERD documentation
```

## Package Manager

**pnpm workspaces** — all packages share a single lockfile (`pnpm-lock.yaml`) at the root. Cross-package imports use the `@ccs-hub/*` namespace.

## Stack

| Layer | Technology | Rationale |
|---|---|---|
| API runtime | Node.js 20 LTS + Express 4 | Mature, well-documented, easy to onboard junior devs |
| API language | TypeScript 5 (strict mode) | Type safety end-to-end |
| ORM / migrations | Drizzle ORM + drizzle-kit | Generates versioned SQL migration files, type-safe queries, no magic |
| Database | PostgreSQL 16 | ACID, `btree_gist` for exclusion constraints, `pg_trgm` / tsvector for FTS |
| Auth | JWT (access + refresh tokens) with argon2id password hashing | Industry-standard; argon2 is the winner of the Password Hashing Competition |
| Email (dev) | Mailpit | Local SMTP + web UI; no external service needed in dev |
| Web app | React 18 + Vite + TanStack Query | Fast dev builds; server-state management |
| Mobile app | Expo 51 + Expo Router | File-based routing; OTA updates; iOS + Android from one codebase |
| Shared types | `@ccs-hub/shared` package | Zod schemas validated on both client and server |
| Container | Docker Compose | One command to start Postgres + Mailpit for local development |

## Design Decisions

### 1. UUIDs as Primary Keys
All tables use `uuid` PKs generated by `uuid_generate_v4()` (via the `uuid-ossp` extension). UUIDs:
- Are safe to generate on the client/mobile before an insert
- Avoid sequential enumeration attacks
- Simplify data synchronization across services

### 2. Drizzle ORM over raw SQL or Prisma
- Generates **versioned, committed SQL migration files** in `apps/api/src/db/migrations/`
- Provides **type-safe query building** without hiding what SQL is being run
- `drizzle-kit studio` offers a visual DB browser during development
- No runtime schema parsing overhead (unlike Prisma)

### 3. JWT Access + Refresh Token Pattern
- Access tokens expire in 15 minutes (configurable via `JWT_ACCESS_EXPIRES_IN`)
- Refresh tokens are stored **hashed** in the `refresh_tokens` table and expire in 7 days
- Rotation: issuing a new refresh token invalidates the previous one
- Logout: the refresh token row is marked `revoked = true`

### 4. Consultation Slot Double-Booking Prevention
Slots are fixed 30-minute blocks. At the database level, an **exclusion constraint** using `btree_gist` prevents two approved/pending consultation requests from overlapping for the same faculty member on the same date:

```sql
ALTER TABLE consultation_requests
  ADD CONSTRAINT no_double_booking
  EXCLUDE USING gist (
    faculty_id WITH =,
    requested_date WITH =,
    tsrange(
      (requested_date || ' ' || start_time)::timestamp,
      (requested_date || ' ' || end_time)::timestamp
    ) WITH &&
  )
  WHERE (status NOT IN ('declined', 'cancelled'));
```

This constraint is added manually in the migration SQL since Drizzle does not natively generate `EXCLUDE` constraints.

### 5. Full-Text Search on Research Studies
A `tsvector` column (`search_vector`) is maintained by a PostgreSQL trigger that fires on INSERT/UPDATE to `research_studies`. A GIN index on this column enables sub-millisecond full-text search using `to_tsquery`. The trigger and index are added in the migration SQL.

### 6. Event QR Attendance
When a student registers for an event, the API generates a signed JWT (`qrPayload`) containing the registration ID and event ID. The scanner (faculty/staff device) calls a verify endpoint that decodes the JWT, marks `attendance_status = 'attended'`, and sets `attended_at`.

## API Conventions

- Base path: `/api/v1`
- Authentication: `Authorization: Bearer <access_token>` header
- Error responses: `{ "error": "...", "message": "...", "statusCode": N }`
- Validation: Zod schemas from `@ccs-hub/shared` are used in both request parsing and client-side forms

## Environment Configuration

Copy `.env.example` to `.env` and fill in the values. The API validates all required environment variables at startup using Zod (`apps/api/src/config/env.ts`) and exits immediately if any are missing or malformed.

## Local Development Quickstart

```bash
# 1. Start infrastructure
docker compose up -d

# 2. Install dependencies
pnpm install

# 3. Copy and configure env
cp .env.example apps/api/.env
# Edit apps/api/.env with your values

# 4. Run migrations (first time)
pnpm db:migrate

# 5. Seed the database
pnpm db:seed

# 6. Start the API
pnpm dev:api

# 7. Start the web app (separate terminal)
pnpm dev:web
```

Services after `docker compose up -d`:
- PostgreSQL: `localhost:5432`
- Mailpit SMTP: `localhost:1025`
- Mailpit Web UI: `http://localhost:8025`
- pgAdmin (optional): `docker compose --profile pgadmin up -d` → `http://localhost:5050`
